# autopost-failover

Оркестратор резервного развёртывания для [autopost](https://github.com/davnozdu/autopost).

Когда дома пропадает интернет и домашний сервер (QNAP) перестаёт отвечать, этот
репозиторий по расписанию поднимает временный резервный сервер на Hetzner Cloud из
образа `ghcr.io/davnozdu/autopost:latest`, накатывает туда снимок БД из приватного
бэкап-репозитория и продолжает постинг. Когда домашний сервер оживает — резерв
гасится и удаляется.

**Почему отдельный публичный репозиторий:** на публичных репозиториях минуты GitHub
Actions бесплатны/безлимитны (ежечасный сторож не ест лимит приватного autopost), а
адрес дома и токены лежат в секретах, не в коде. Обратная сторона: **логи прогонов
видны всем** — поэтому скрипты ничего секретного в лог не печатают (root-пароль
сервера маскируется и уходит только в Telegram).

## Этапы

- **Этап 3 (готово):** `scripts/watchdog.sh` + workflow `watchdog.yml` — ежечасная
  проверка `/health` домашнего сервера с подтверждением отключения (3 попытки ×
  10 мин) и уведомлением в Telegram.
- **Этап 4 (готово):** `scripts/provision.sh` — при `HOME_DOWN` создаёт самый дешёвый
  доступный почасовой x86-сервер Hetzner, ставит Docker через cloud-init и запускает
  контейнер; тот сам восстанавливает БД/настройки из бэкап-репо и продолжает постинг.
- **Этап 5 (дальше):** `scripts/teardown.sh` — при `HOME_UP` слить свежую БД обратно
  в бэкап и удалить резервный сервер. Наличие сервера в Hetzner = состояние (не нужно
  отдельное хранилище флагов).

## Как работает Этап 4

1. Сторож подтвердил `HOME_DOWN`.
2. `provision.sh` смотрит, нет ли уже сервера с меткой `role=autopost-failover`
   (идемпотентность — двух резервов не будет).
3. Спрашивает у Hetzner API список тарифов и ЦОДов, выбирает **самый дешёвый по
   часовой цене доступный** тариф с архитектурой **x86** (образ autopost собирается
   только под `linux/amd64` — ARM-тарифы `CAX…` не подойдут), RAM ≥ 2 ГБ, диск ≥ 20 ГБ.
   Обычно это `cx22` (~€0,0075/час ≈ €4,5/мес + ~€0,60/мес за IPv4). Тариф можно
   зафиксировать переменной `SERVER_TYPE`.
4. Создаёт сервер с cloud-init: ставит Docker (если образ ОС без него), пишет
   `/opt/autopost/.env` (chmod 600), `docker pull` публичного образа GHCR и `docker run`
   с томами `/opt/autopost/data` и `/opt/autopost/site`, порт `8778`.
5. Контейнер стартует с **пустым томом** → `app/bootstrap.py` видит `BACKUP_REPO` +
   `BACKUP_TOKEN` и восстанавливает снимок БД (или, если снимка нет, хотя бы настройки
   из JSON-бэкапа) — вместе с ключом основного LLM и токеном доступа.
6. Скрипт ждёт ответа `http://<IP>:8778/health` (до 12 мин) и шлёт в Telegram адрес
   резерва. Вход в админку — `http://<IP>:8778/?access=<токен доступа>`; токен тот же,
   что дома (он в бэкапе БД), поэтому запоминать новый не нужно.

Если `/health` не ответил — сервер **не удаляется**, чтобы можно было зайти и
посмотреть `docker logs autopost` (root-пароль придёт в Telegram, либо заранее заведите
SSH-ключ в проекте Hetzner и укажите его имя в переменной `SSH_KEY_NAME`).

## Секреты репозитория

| Секрет | Назначение | Этап |
|--------|-----------|------|
| `HOME_HEALTH_URL` | URL проверки дома, напр. `http://myhome.duckdns.org:8778/health` | 3 |
| `TG_BOT_TOKEN` | токен Telegram-бота для уведомлений (опционально) | 3 |
| `TG_CHAT_ID` | chat_id для уведомлений (опционально) | 3 |
| `HCLOUD_TOKEN` | API-токен проекта Hetzner Cloud, **Read & Write** | 4 |
| `BACKUP_REPO` | `owner/name` приватного бэкап-репо (`davnozdu/autopost-config-backup`) | 4 |
| `BACKUP_TOKEN` | GitHub PAT к бэкап-репо, **Contents: read and write** (резерв и сам бэкапит) | 4 |
| `SECRET_KEY` | тот же ключ сессий, что дома (иначе не совпадут куки/подписи) | 4 |
| `API_KEY` | ключ HTTP API, если нужен на резерве (опционально) | 4 |
| `REMOTE_ACCESS_TOKEN` | токен гейта; можно не задавать — подтянется из бэкапа БД | 4 |

## Переменные репозитория (Settings → Variables)

| Переменная | По умолчанию | Смысл |
|------------|--------------|-------|
| `FAILOVER_ENABLED` | *(нет)* | **Предохранитель.** Пока не `true`, резерв НЕ поднимается — сторож только детектит и шлёт уведомление |
| `SERVER_TYPE` | *(авто)* | зафиксировать тариф, напр. `cx22` |
| `LOCATIONS` | `fsn1,nbg1,hel1` | приоритет локаций |
| `PORT` | `8778` | внешний порт резерва |
| `TZ` | `Europe/Prague` | таймзона планировщика |
| `SSH_KEY_NAME` | *(нет)* | имя SSH-ключа в проекте Hetzner для ручного дебага |
| `BACKUP_BRANCH` | `main` | ветка бэкап-репо |

## Ручной тест

Actions → **Watchdog** → **Run workflow**:

- `retry_interval = 5` — быстрая проверка детекта, не ждать 10 минут;
- `dry_run = true` + `force_provision = true` — показать, какой тариф и за сколько был бы
  создан, **ничего не создавая** (нужен только `HCLOUD_TOKEN`; `FAILOVER_ENABLED=true`
  всё равно требуется);
- `force_provision = true` — реально поднять резерв, не проверяя дом.

## Удалить резерв вручную (пока нет Этапа 5)

Автоматического гашения ещё нет — не забудьте удалить сервер, иначе он тикает по
€0,0075/час:

```bash
ID=$(curl -s -H "Authorization: Bearer $HCLOUD_TOKEN" \
  "https://api.hetzner.cloud/v1/servers?label_selector=role%3Dautopost-failover" \
  | jq -r '.servers[0].id')
curl -s -X DELETE -H "Authorization: Bearer $HCLOUD_TOKEN" \
  "https://api.hetzner.cloud/v1/servers/$ID"
```

Либо кнопкой в консоли Hetzner Cloud. **Перед удалением** убедитесь, что резерв успел
залить свежую БД в бэкап-репо (в админке резерва: Настройки → «Бэкап БД» → «Сделать
бэкап сейчас»), иначе посты, сделанные на резерве, потеряются.
