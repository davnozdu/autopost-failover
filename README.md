# autopost-failover

Оркестратор резервного развёртывания для [autopost](https://github.com/davnozdu/autopost).

Когда дома пропадает интернет и домашний сервер (QNAP) перестаёт отвечать, этот
репозиторий по расписанию поднимает временный дроплет на DigitalOcean из образа
`ghcr.io/davnozdu/autopost:latest`, накатывает туда снимок БД из приватного
бэкап-репозитория и продолжает постинг. Когда домашний сервер оживает — свежая база
уезжает домой, а дроплет удаляется.

**Почему отдельный публичный репозиторий:** на публичных репозиториях минуты GitHub
Actions бесплатны/безлимитны (ежечасный сторож не ест лимит приватного autopost), а
адрес дома и токены лежат в секретах, не в коде. Обратная сторона: **логи прогонов
видны всем** — поэтому скрипты ничего секретного в лог не печатают.

## Сколько это стоит

Платится только время, пока дом лежит. Тариф по умолчанию `s-1vcpu-1gb`
(1 vCPU, 1 ГБ RAM, 25 ГБ SSD):

| | |
|---|---|
| **$0,00893/час** | ~$0,21 за сутки простоя |
| $6/мес | если бы работал непрерывно весь месяц |

Публичный IPv4 у DigitalOcean входит в цену дроплета (отдельно не тарифицируется),
бэкапы и мониторинг выключены при создании.

1 ГБ RAM для autopost впритык: монтаж видео-сториз через ffmpeg может упереться в
память. Поэтому cloud-init включает **файл подкачки на 2 ГБ** — это дешевле, чем брать
вдвое более дорогой тариф. Если сториз много и они будут тормозить, поставьте
переменную `SIZE_SLUG = s-1vcpu-2gb` ($12/мес = $0,0179/час).

## Этапы

- **Этап 3 (готово):** `scripts/watchdog.sh` + workflow `watchdog.yml` — ежечасная
  проверка `/health` домашнего сервера с подтверждением отключения (3 попытки ×
  10 мин) и уведомлением в Telegram.
- **Этап 4 (готово):** `scripts/provision.sh` — при `HOME_DOWN` создаёт дроплет,
  ставит Docker через cloud-init и запускает контейнер; тот сам восстанавливает
  БД/настройки из бэкап-репо и продолжает постинг.
- **Этап 5 (готово):** `scripts/teardown.sh` — при `HOME_UP` забирает свежую БД с
  резерва, передаёт её домой и удаляет дроплет. Наличие дроплета с тегом
  `autopost-failover` = состояние (отдельное хранилище флагов не нужно).

## Как работает Этап 4

1. Сторож подтвердил `HOME_DOWN`.
2. `provision.sh` смотрит, нет ли уже дроплета с тегом `autopost-failover`
   (идемпотентность — двух резервов не будет).
3. Спрашивает у DO API список тарифов (`/v2/sizes`), отбирает доступные с RAM ≥ 1 ГБ и
   диском ≥ 20 ГБ в выбранных регионах и строит очередь: сначала предпочтительный
   `SIZE_SLUG`, дальше по возрастанию цены. Флаг «доступен» у провайдеров бывает
   неточным, поэтому при отказе на создании скрипт пробует следующего кандидата
   (до 6 попыток), а не падает.
4. Создаёт дроплет с cloud-init: своп 2 ГБ, Docker (если образ ОС без него),
   `/opt/autopost/.env` с правами 600, `docker pull` публичного образа GHCR и
   `docker run` с томами `/opt/autopost/data` и `/opt/autopost/site`, порт `8778`.
5. Контейнер стартует с **пустым томом** → `app/bootstrap.py` видит `BACKUP_REPO` +
   `BACKUP_TOKEN` и восстанавливает снимок БД (или, если снимка нет, хотя бы настройки
   из JSON-бэкапа) — вместе с ключом основного LLM и токеном доступа.
6. Скрипт ждёт ответа `http://<IP>:8778/health` (до 12 мин) и шлёт в Telegram адрес
   резерва. Вход в админку — `http://<IP>:8778/?access=<токен доступа>`; токен тот же,
   что дома (он в бэкапе БД), поэтому запоминать новый не нужно.

Если `/health` не ответил — дроплет **не удаляется**, чтобы можно было зайти и
посмотреть `docker logs autopost`. Для этого заранее заведите SSH-ключ в аккаунте DO и
укажите его имя в переменной `SSH_KEY_NAME`: без ключа попасть на сервер можно только
через веб-консоль DO со сбросом root-пароля.

## Как работает Этап 5

Сторож увидел `HOME_UP`, а дроплет ещё жив. Порядок жёсткий — **сначала спасаем
данные, потом удаляем**:

1. Резерв проверяется на живость (`/health`). Не отвечает трижды → он и не постил,
   спасать нечего: дроплет удаляется, дом остаётся главным.
2. `POST http://<резерв>:8778/api/scheduler/pause` — **публикации на резерве
   останавливаются**. Снимок должен быть финальным: всё, что резерв опубликует после
   снимка, не доедет домой, и дом выдаст те же новости повторно.
3. `POST http://<резерв>:8778/api/db-backup?force=true` — форсированный снимок БД в
   бэкап-репозиторий (`force` игнорирует выключатель регулярного бэкапа).
4. Проверка по GitHub API, что коммит `autopost-db.sqlite.gz` реально свежий
   (не старше 30 мин) — на случай, если резерв отрапортовал успех, а файл не доехал.
5. **Сверка «кто новее».** У обоих читается `last_published` из `/api/status`. Если на
   резерве нет публикаций свежее домашних — базу домой **не везём**: значит резерв
   отработал вхолостую (например, дом на самом деле работал, но был недоступен из
   интернета — сбой маршрута или DDNS), и его старая копия откатила бы домашние посты.
   Обойти можно переменной `FORCE_HOME_RESTORE=1`.
6. `POST http://<дом>:8778/api/db-restore?confirm=true` — дом скачивает снимок, кладёт
   его рядом как «ожидающий» и **гасит себя по SIGTERM**. Docker с
   `restart: unless-stopped` поднимает контейнер, и на старте
   `bootstrap.apply_pending_restore` подставляет базу (прежняя сохраняется как
   `autopost.db.pre-restore`). Подменять живую SQLite на ходу нельзя — отсюда манёвр.
7. Ждём возврата `/health` дома (до 5 мин) и только тогда **удаляем** дроплет.

**Только удаление, никаких poweroff/shutdown.** Выключенный дроплет DigitalOcean
продолжает тарифицироваться — ресурсы за ним зарезервированы; счётчик останавливает
именно destroy. Поэтому `teardown.sh`:

- шлёт `DELETE /v2/droplets/{id}` и **дожидается, пока дроплет реально исчезнет из API**
  (удаление асинхронное, ждём до ~100 с);
- делает финальную сверку, что дроплетов с тегом `autopost-failover` не осталось;
- проверяет, не появилось ли снапшотов резерва (они тарифицируются отдельно);
- если хоть что-то не сошлось — шаг падает красным и в Telegram приходит «снесите
  вручную», а не молчаливое «всё хорошо».

**Любой сбой на шагах 3–6 оставляет резерв жить и СНИМАЕТ с него паузу** — он
продолжает постить за главного. Потерять посты, сделанные на резерве, хуже, чем
заплатить лишние центы за час; причина придёт в Telegram.

Зачем шаг 4 вообще: дом стартует с НЕпустым томом, поэтому обычный
`bootstrap.pre_init_restore` его не трогает — без явной передачи базы дом продолжил бы
со своей устаревшей и выдал бы уже опубликованные новости по второму разу.

⚠️ Ручки `/api/db-backup`, `/api/db-restore`, `/api/scheduler/pause|resume` и поле
`last_published` в `/api/status` появились в образе autopost вместе с Этапом 5 —
**дома нужен контейнер из свежего образа**, иначе возврат домой не сработает
(гашение при этом безопасно остановится и не удалит резерв).

## Секреты репозитория

| Секрет | Назначение | Этап |
|--------|-----------|------|
| `HOME_HEALTH_URL` | URL проверки дома, напр. `http://myhome.duckdns.org:8778/health` | 3 |
| `TG_BOT_TOKEN` | токен Telegram-бота для уведомлений (опционально) | 3 |
| `TG_CHAT_ID` | chat_id для уведомлений (опционально) | 3 |
| `DO_TOKEN` | Personal Access Token DigitalOcean, **Read + Write** | 4 |
| `BACKUP_REPO` | `owner/name` приватного бэкап-репо (`davnozdu/autopost-config-backup`) | 4 |
| `BACKUP_TOKEN` | GitHub PAT к бэкап-репо, **Contents: read and write** (резерв и сам бэкапит) | 4 |
| `SECRET_KEY` | тот же ключ сессий, что дома (иначе не совпадут куки/подписи) | 4 |
| `API_KEY` | ключ HTTP API; **обязателен для Этапа 5** (возврат базы домой) | 4 |
| `REMOTE_ACCESS_TOKEN` | токен гейта для входа в админку резерва. **Задайте тот же, что дома**: если дома он приходит из переменной окружения (а не из настроек в БД), в бэкапе его нет, и резерв сгенерирует новый — прочитать его можно будет только из `docker logs` по SSH | 4 |

## Переменные репозитория (Settings → Variables)

| Переменная | По умолчанию | Смысл |
|------------|--------------|-------|
| `FAILOVER_ENABLED` | *(нет)* | **Предохранитель.** Пока не `true`, резерв НЕ поднимается — сторож только детектит и шлёт уведомление |
| `SIZE_SLUG` | `s-1vcpu-1gb` | тариф дроплета ($6/мес); `s-1vcpu-2gb` — вдвое больше памяти |
| `REGIONS` | `fra1,ams3,lon1` | приоритет регионов |
| `SWAP_GB` | `2` | размер файла подкачки на резерве |
| `PORT` | `8778` | внешний порт резерва |
| `TZ` | `Europe/Prague` | таймзона планировщика |
| `SSH_KEY_NAME` | *(нет)* | имя SSH-ключа в аккаунте DO для ручного дебага |
| `BACKUP_BRANCH` | `main` | ветка бэкап-репо |
| `SKIP_HOME_RESTORE` | `0` | `1` — при гашении не передавать базу домой (дом останется со своей) |
| `FORCE_HOME_RESTORE` | `0` | `1` — везти базу домой даже если на резерве нет публикаций новее |
| `OS_IMAGE` | *(авто)* | образ ОС дроплета, по умолчанию свежая Ubuntu LTS |

## Ручной тест

Actions → **Watchdog** → **Run workflow**:

- `retry_interval = 5` — быстрая проверка детекта, не ждать 10 минут;
- `dry_run = true` + `force_provision = true` — показать очередь тарифов и цену,
  **ничего не создавая** (нужен только `DO_TOKEN`; `FAILOVER_ENABLED=true` всё равно
  требуется);
- `force_provision = true` — реально поднять резерв, не проверяя дом;
- `force_teardown = true` — прогнать возврат домой и удаление, не проверяя дом;
- `force_teardown = true` + `keep_server = true` — прогнать весь возврат (бэкап →
  передача домой → перезапуск дома), но **дроплет не удалять**.

## Удалить резерв вручную

Штатно это делает Этап 5. Аварийно (например, удаление остановилось из-за сбоя и
предупредило об этом в Telegram):

```bash
ID=$(curl -s -H "Authorization: Bearer $DO_TOKEN" \
  "https://api.digitalocean.com/v2/droplets?tag_name=autopost-failover" \
  | jq -r '.droplets[0].id')
curl -s -X DELETE -H "Authorization: Bearer $DO_TOKEN" \
  "https://api.digitalocean.com/v2/droplets/$ID"
```

Либо кнопкой Destroy в консоли DigitalOcean. **Перед удалением** убедитесь, что резерв
успел залить свежую БД в бэкап-репо (в админке резерва: Настройки → «Бэкап БД» →
«Сделать бэкап сейчас»), иначе посты, сделанные на резерве, потеряются.
